Mission 04

社群經營 · 活動統籌
從零到百人實體賽事

FOL 生命之火：玩家社群與線下賽事

語音平台停止服務後，《黎明死線》玩家少了集中交流的地方。我和實況主、社群夥伴一起建立 Discord 社群，再把線上的熱度延伸成線下賽事。

ON AIRCH.07 · FOL 生命之火 賽事紀錄
SRC · YouTube @fol7930
10,000+暑假一個月的社群規模
100+賽事當日到場人數
NT$3,000場地租金，以自己的直播收益支付
YouTube 頻道 ↗ Twitch ariestv ↗

我的角色

活動統籌。負責場地洽談與場勘、邀請實況主宣傳、遠端協調人力、現場設備備援（賽制由合作戰隊設計）

PROBLEM

遊戲熱度上升、台灣玩家變多，但原本常用的語音平台停止服務，玩家缺少集中交流和比賽的空間。

APPROACH

擔任共同創辦人、活動統籌與直播主。協調活動流程（賽制由合作戰隊設計），邀請實況主宣傳，安排場地、主持與現場人力，並用 Discord 協調分散各地的成員。

RESULT

社群在暑假一個月內成長到破萬人；線下賽事當日到場超過百人，之後的直播與社群熱度也延續下去。

社群經營活動統籌跨角色協作現場應變
看完整案例：執行過程與現場應變
執行過程
  • 需求觀察：發現玩家缺少交流空間與線下活動
  • 社群啟動：透過實況主與玩家導流，一個月內破萬人
  • 活動籌備：與合作戰隊確認賽制、找場地、電話聯絡、場勘，安排主持與人力
  • 宣傳與直播：串聯多位實況主推廣，用自己的 Twitch 收益墊付場租
挑戰：開場前直播設備故障導播電腦連不上 Twitch。因為事先準備了備用筆電，立即排查並回家取備機，在開場前排除問題。
挑戰：團隊成員分散各地成員不在同一個城市，用 Discord 固定回報進度、分配任務，確保籌備進度一致。
挑戰：預算有限沒有贊助的情況下，用直播收益支付場地租金，讓活動能如期舉辦。

Mission 06

遊戲營運分析 · 玩家體驗
探索性研究（2026/10）

《三角洲行動》營運分析：撤離模式的風險不對稱

我的角色

獨立研究。資料蒐集、評論分類設計、證據強度標示、改善方案規劃（評論分類以 AI 協助）

PROBLEM

以公開資料對 Garena 代理的《三角洲行動》進行探索性研究，觀察撤離模式中一般玩家的體驗問題。

APPROACH

  • 整理 Steam 每月平均在線人數（2026/5–10），觀察到賽季中段約下滑 23%
  • 用 AI 分類約 94 則玩家評論，對照官方安全公告與媒體報導
  • 每項論點標示證據強度，證據不足的論點不納入

RESULT

提出「風險分層配對」與「以風險管理為核心的新手引導」兩項方案，附成效指標與風險評估，作為後續驗證依據。

研究限制｜待驗證的假設

Steam 數據只反映部分 PC 玩家，不代表 Garena 代理版整體；在線人數下滑也不等於玩家流失，結論屬於待驗證的假設。

Mission 01

AI 視覺 · 品質管理
實際工作專案

品牌 AI 海報品管系統

為農機品牌製作社群海報與文案。AI 生圖速度快，但品牌混淆、產品外觀錯誤這類問題，靠肉眼一張張判斷既慢又不穩定，所以我把判斷方式整理成一套固定標準。

我的角色

獨立負責。需求確認、提示詞設計、制定 A–D 品管標準、人工修正、建立歸檔規則

PROBLEM

初期約 40% 的海報需要重新生成（每 10 張約 4 張）。常見錯誤包含品牌混淆、產品結構走樣、型號貼紙錯誤，以及要仔細比對才看得出的細節瑕疵。

APPROACH

以官方產品圖為辨識基準，規定 AI 不可改動結構、Logo 與型號；再用 A–D 四級分類決定每張圖是直接交付、小修、重生還是退件。

RESULT

需重新生成的比例降至接近 0；目前每 10 張約 1–2 張僅需細部小修即可交付。搭配比例命名與版本封存規則，多品牌、多品項都用同一套標準交付。

A
直接交付產品與品牌正確，版面完整
B
人工小修瑕疵可控，修正後交付
C
重新生成構圖或資訊層級需重做
D
退件產品結構或品牌錯誤
導入前
~40%
導入後
≈0

重新生成比例 = C 級＋D 級張數 ÷ 總產出張數（個人工作紀錄估算）

實例：同一張海報，品管前後（局部）

AI 原始生成品管修正後 ⇆
找到的問題EC-04 被標成「2 吋抽水機」；GP160、GX160 引擎面板上出現 AI 自己生成的亂碼貼紙。
修正結果規格改回「1 吋」，引擎外觀依官方產品圖重新生成，其餘版面保持不變。
AI 圖像生成品質標準設計品牌一致性檔案版本管理
看完整案例：判斷順序與交付流程
判斷順序：先看會不會出錯，再看好不好看
  • 品牌與產品是否正確？Logo、型號、產品結構有錯 → 直接列為 D 級退件
  • 錯誤能不能人工修正？可控的小瑕疵 → B 級，修完交付
  • 是不是構圖或資訊層級的結構問題？→ C 級，調整提示詞後重新生成
挑戰：錯誤藏在細節裡型號貼紙、規格數字這類錯誤，縮圖時看不出來。解法是交付前一律放大比對官方產品圖。
挑戰：多品牌容易混淆同時處理多個品牌時，AI 會把 A 品牌的元素畫到 B 品牌產品上。解法是每次生成只給單一品牌的官方素材。
挑戰：版本越存越亂同一主題有多個比例與版本。解法是固定命名「主題_比例_版本」，舊版移到封存資料夾，不直接刪除。
交付流程

需求與官方素材確認 → 生成與構圖 → A–D 品管 → 人工修正 → 命名與歸檔 → 排程發布

→

架構示意｜下一階段：串接 n8n 自動化與 Facebook 排程

我的角色

流程設計與驗證。決定 Claude 與 GPT 分工、規劃分階段測試、發現多商品欄位缺口並決定升級格式、制定 QA 規則（JSON 格式由 GPT 依我的需求產出）

PROBLEM

多個 AI 之間靠自然語言交接，欄位常漏、格式不一，自動化工具也無法穩定讀取。

APPROACH

先用文字表格測 2 篇，確認分工可行後才升級為正式 JSON 格式；測試中發現「一篇貼文多個商品」的缺口，當場加上商品陣列欄位。

交接格式範例（模擬資料）
{
  "post_id": "POST-20261003-01",
  "content_type": "event_post",
  "campaign_stage": "promotion",
  "products": ["產品A", "產品B"],
  "image_type": "product_combo",
  "status": "ready_for_image"
}

8 種貼文類型、7 種行銷階段、8 個製作狀態皆為固定值；修改任何欄位需雙方同步，不能單方面變更。

RESULT

跑完 14 篇、8 種貼文類型的完整流程，產出可重複使用的交接格式、文案規格範本與雙 AI 同步回報機制。

Multi-AI 協作JSON Schema內容日曆Prompt 設計
看完整案例：遇到的問題與取捨
挑戰：文字表格交接不穩定人看得懂，但欄位名稱和格式每次不同，自動化工具讀不了。改由 GPT 設計正式 JSON 格式，固定 8 種貼文類型、7 種活動階段與貼文編號規則，雙方都依這份格式交接。
挑戰：格式沒考慮多商品貼文節慶貼文常同時推多個商品，原本的單一商品欄位放不下。第一輪只測 3 篇就發現，立刻加上商品陣列欄位升級到 v1.1，避免 14 篇全部送出後才整批重工。
挑戰：縮圖檢查會誤判用縮圖比對時有 3 張被判定不符，放大確認後其實都符合規格。之後規定以放大檢視為準，省下不必要的重新生成。
為什麼這樣取捨
  • 先用模擬品牌跑通流程，不等真實資料：這個 MVP（最小可行產品）要驗證的是流程本身
  • 先人工複製貼上交接，暫不接 n8n：分工和格式確認無誤，才值得投入自動化
  • 格式邊測邊改：實際測出來的問題，比事先猜測所有情況更有效率
下一步

接上真實商品資料、串接 n8n 讓文案直接觸發生圖，最後補上 Facebook 自動排程。

可運作的網頁原型

企業部門 AI 助理原型

企業直接開放通用聊天機器人，任何部門都可能問出其他部門的薪資或報價。這個原型示範如何在大型語言模型前面加一層規則，讓 AI 知道自己該答什麼、不該答什麼。

↓

人資規則＋人資知識庫

SALES ASSISTANT
業務規則＋產品知識庫

問員工請假資料 → 拒答並說明

↓
CORE RULES · 全域規則，使用者無法覆寫
身分邊界、跨部門資料隔離、不捏造資訊、需核准事項只建議不代決

CLAUDE API
依規則做語意層級的權限判斷後回應

架構示意｜Next.js＋TypeScript＋Claude API，以 Claude Code 協作開發

我的角色

需求定義與架構決策。設計三層規則架構、撰寫部門規則、規劃並驗收雙向測試（程式由 Claude Code 協作實作）

PROBLEM

通用 AI 助理沒有部門邊界，有跨部門資訊外洩與越權回答的風險。

APPROACH

分成全域規則、部門規則、部門知識庫三層。先用固定回應驗證資料流，確認架構正確後才接真實模型。

RESULT

雙向跨部門測試通過：HR 問業務價格、Sales 問人事資料，都被正確拒答並附上轉介建議。

AI Solution Design權限控制Claude APINext.js
看完整案例：遇到的問題與取捨
挑戰：兩個部門的規則檔搞混HR 與 Sales 都有同名的規則檔和知識庫檔，下載時被自動加上流水號，分不清哪份屬於哪個部門。改用終端機指令直接寫入正確路徑，不再靠肉眼辨識檔名。
挑戰：接上模型後還是顯示假回應環境變數已經設定，但呼叫模型的程式其實還沒改，加上瀏覽器快取。明確要求修改呼叫邏輯並清除快取後，成功切換為真實回應。
驗證方式做雙向跨部門測試：HR 問產品價格、Sales 問員工請假資料，兩邊都要被拒答，並說明原因、建議轉介窗口。
為什麼這樣取捨
  • 先用固定回應驗證架構，再接真實模型：避免一開始就卡在 API 申請與費用設定
  • 不做多代理、複雜檢索或單一登入：原則是「能跑 → 完整 → 複雜」，先驗證核心概念
  • 使用模擬知識庫：這是概念驗證階段，重點是權限邏輯，不是資料整合
下一步

擴充到財務、客服等更多部門，加入對話紀錄與人工審核介面，並評估讓知識庫隨業務資料即時更新。
